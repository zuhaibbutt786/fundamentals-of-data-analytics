Lecture 3: Data Acquisition Types & Storage

Understand the shapes data comes in, the common file and database formats, how analysts actually acquire data, and how to choose storage that matches the problem.

1. Learning Objectives

By the end of this lecture you will be able to:

  • 1 Classify data as structured, semi-structured, or unstructured and give concrete examples of each.
  • 2 Work confidently with common acquisition formats: CSV, Excel, JSON, Parquet, and relational databases.
  • 3 Explain the relational model at a conceptual level (tables, primary keys, foreign keys, relationships).
  • 4 Describe ethical and technical considerations around web scraping and API usage.
  • 5 Choose an appropriate storage approach (file, database, lake, warehouse) for a given analytics problem.

2. Motivation — Why Acquisition Comes First

Before any cleaning, transformation, or dashboard work, data must be acquired. The form it arrives in determines how much work the rest of the pipeline will need. Treating a nested JSON API response the same way as a clean CSV will produce frustration, silent errors, and delayed projects.

Professionals spend a surprising amount of time negotiating cleaner extracts, documenting lineage, and choosing the right landing zone. This lecture builds the vocabulary and decision-making skill you need at the start of every project.

💡 Key Insight
Acquisition is not “just download the file.” It is the first design decision of the pipeline: source reliability, schema stability, volume, velocity, and legal constraints all influence what you store and how you transform it later.

3. Real-World Story

The “Simple” Excel Export That Wasn’t

An analyst was asked to build a sales dashboard from “one Excel file from finance.” The file contained three sheets, merged cells in the header, a title row that changed every month, numbers stored as text with currency symbols, and a hidden sheet of adjustments. What looked like a 30-minute task became a multi-day cleaning exercise and delayed the dashboard by a week.

Recognizing data shape and quality early — and negotiating cleaner extracts or an automated feed — is a core acquisition skill. The same story appears in healthcare (messy EHR exports), banking (legacy mainframe flat files), and e-commerce (inconsistent product catalog dumps).

4. Problem Statement

Given a business question, how do you decide:

  • Where the data currently lives?
  • What shape it is in (structured / semi-structured / unstructured)?
  • Which format and protocol to request (CSV, API, database query, file share)?
  • Where to land it first (local file, object storage, staging database, lake)?
  • What ethical and legal constraints apply?

Wrong answers here create downstream rework that no amount of clever Pandas or DAX can fully erase.

5. Theory — Structured vs Semi-structured vs Unstructured

Almost every textbook and industry guide organizes data into three broad shapes. Understanding them is the foundation of acquisition design.

Easy Explanation

Structured data fits neatly into tables with fixed columns. Think of a spreadsheet of student grades or a POS transaction table. Semi-structured data has labels (keys or tags) but the structure can nest and vary from record to record — JSON from an API is the classic example. Unstructured data has no predefined model; extracting value usually requires NLP, computer vision, or human labeling.

Deep Explanation

In practice the boundaries blur. A “structured” Excel file may contain free-text comments and merged cells. A JSON document may follow a strict schema enforced by an API contract. Modern lakes often store everything as files first (bronze) and impose structure later (silver/gold). The taxonomy still helps you ask the right questions: Do I already have a stable schema? How nested is it? Will I need specialized extraction?

8. Relational Model Essentials

Most business data still lives in relational databases. Even when you receive a flat CSV, it often came from a relational source. Core ideas:

  • Table (relation) — a set of rows with a fixed set of columns.
  • Primary key — uniquely identifies each row (never null, never duplicate).
  • Foreign key — a column that references a primary key in another table; this is how relationships are expressed.
  • Normalization — reducing redundancy by splitting data into related tables (you will deepen this in Module 5 modeling lectures).
Analyst tip
When you receive data from a database, always ask for the data dictionary or ER diagram. Knowing which columns are keys and which tables join together saves hours of trial-and-error joins.

9. Web Scraping — Concepts & Ethics

Web scraping means programmatically extracting information from websites. It is powerful and also easy to misuse. Treat it as a last resort after APIs and official exports.

  • Prefer official APIs when they exist — they are more stable and usually come with documentation and rate limits.
  • Respect robots.txt and the site’s terms of service.
  • Do not overload servers; add delays, caching, and backoff.
  • Never scrape personal data without a lawful basis and clear purpose.
  • Store the acquisition date and source URL for every record (lineage and auditability).

In later practicals you will see how libraries such as BeautifulSoup are used for HTML parsing; the principles above always come first. Ethics and legality are not optional extras — they are part of professional practice (CLO-5).

Common Mistakes
  • Scraping because “the data is visible in the browser” without checking terms
  • Ignoring rate limits and getting blocked or banned
  • Storing personal identifiers without a retention and access policy
  • Failing to record source and timestamp, making results unreproducible

10. Industry Examples — How Acquisition Looks in Practice

Retail / E-commerce

POS transactions arrive as nightly CSV or direct database replication. Product catalogs may come from a PIM system via JSON API. Web clickstream is often semi-structured event logs landed in a lake.

Healthcare

EHR extracts are frequently messy Excel or HL7/FHIR messages (semi-structured). Imaging is unstructured. Strict privacy rules govern what can be acquired and where it may be stored.

Banking / Fintech

Core banking systems expose relational tables or secure file drops. Fraud and transaction streams are high-velocity and often landed in real-time or micro-batch pipelines. Regulatory lineage is mandatory.

Sports / Government

Sports analytics may combine structured match stats with unstructured video and text commentary. Government open-data portals often publish CSV and JSON; always check license and update cadence.

You already met the medallion idea (bronze → silver → gold) in Lecture 2. Acquisition almost always lands in bronze first: keep the original files or raw extracts unchanged so you can always reprocess.

12. Python & Pandas — Reading Common Formats

These patterns appear in almost every analytics project. Run them in any environment that has Pandas installed.

import pandas as pd

# CSV (watch encoding and separator)
df_csv = pd.read_csv("sales.csv", encoding="utf-8", sep=",")

# Excel — specify sheet and skip title rows if needed
df_xlsx = pd.read_excel("finance_export.xlsx", sheet_name="Transactions", skiprows=2)

# JSON — flatten nested records when useful
df_json = pd.read_json("api_response.json")
# or for line-delimited JSON:
df_ndjson = pd.read_json("events.jsonl", lines=True)

# Quick shape check after every load
print(df_csv.shape)
print(df_csv.dtypes)
print(df_csv.head())
Expected habit
After every read, print shape, dtypes, and a few rows. Acquisition bugs (wrong sheet, wrong encoding, truncated file) surface here — not three hours later in a dashboard.

13. SQL — Acquiring from a Relational Source

-- Prefer explicit column lists and filters at the source
SELECT
  order_id,
  customer_id,
  order_date,
  amount,
  status
FROM sales.orders
WHERE order_date >= '2025-01-01'
  AND status <> 'cancelled';

-- Always know the grain (one row = one order? one line item?)
-- Ask for the primary key and any foreign keys you will join on later.

14. Excel & Power Query

Many business users still live in Excel. Power Query (Get & Transform) is the professional way to acquire and lightly shape data before it reaches the grid:

  • Connect to folder, web, database, or file.
  • Remove header rows, promote headers, set types.
  • Append or merge queries instead of copy-paste.
  • Load to Data Model when the destination is Power BI or a robust workbook.

You will deepen Power Query skills in the Power BI lectures (L20–L21).

15. Hands-on Lab — Classify & Plan Acquisition

Exercise A — Classify These Sources

For each source, state whether it is structured, semi-structured, or unstructured, and name a suitable storage target:

  1. Daily CSV export of POS transactions
  2. JSON response from a weather API
  3. Collection of PDF invoices
  4. Customer support chat transcripts
  5. Product catalog table in PostgreSQL
Sample Answers +
  1. Structured → warehouse or lake (bronze then curated fact table)
  2. Semi-structured → lake or warehouse with JSON support
  3. Unstructured → object storage / lake; extract fields later with OCR/NLP
  4. Unstructured (text) → lake + NLP pipeline or document store
  5. Structured → already in a database; replicate or query for analytics

Exercise B — Decision Memo

Write a short acquisition plan (5–8 sentences) for this scenario:

“Marketing wants weekly website engagement metrics joined to CRM campaign flags. The web team can give a daily JSON export of page views; CRM is a SQL Server database. Volume is ~2 million events/week.”

Cover: preferred sources, format, landing zone, ethics/permissions, and one risk you will monitor.

18. Flashcards

Structured data example?
SQL tables, clean CSV, Excel ranges with fixed columns, Parquet
Primary key?
A column (or set of columns) that uniquely identifies each row in a table
Semi-structured example?
JSON from APIs, XML, many application logs, NoSQL documents
Why record lineage?
So results are reproducible and auditable — source, timestamp, and transformation history

19. Cheat Sheet

  • Structured → tables, CSV, Parquet · Semi → JSON, XML · Unstructured → text, images, video, PDFs
  • Prefer API / database over scrape; always check ethics and terms
  • Ask for data dictionary, keys, grain, and update frequency
  • Land raw data in bronze first; keep originals
  • After every load: check shape, dtypes, head, and nulls
  • Foreign key lives on the “many” side of a 1:N relationship

20. Common Mistakes & Best Practices

Avoid
  • Assuming “Excel = clean structured data”
  • Scraping without checking terms or robots.txt
  • Loading huge CSVs into memory without sampling first
  • Forgetting to record source and acquisition time
  • Joining tables without knowing keys and grain
Prefer
  • Ask for schema + sample before the full extract
  • Use official APIs and documented exports
  • Land raw → then clean (medallion mindset)
  • Document lineage for every critical table
  • Validate row counts and key uniqueness early

21. Summary

  • Data arrives as structured, semi-structured, or unstructured — know the difference and design acquisition accordingly.
  • CSV, Excel, JSON, Parquet, and SQL databases are the everyday workhorses of acquisition.
  • Relational concepts (primary key, foreign key, grain) are essential even when you work with flat files.
  • Scraping is a last resort; ethics, legality, and lineage come first.
  • Choose storage that matches volume, sharing needs, and downstream tools — and always keep a raw bronze copy.
