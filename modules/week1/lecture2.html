Lecture 2: Designing a Data Pipeline

From raw sources to trusted insights — learn how modern analytics pipelines are architected, the difference between ETL and ELT, warehouses vs lakes, and batch vs real-time processing.

1. Learning Objectives

  • 1 Draw and explain an end-to-end analytics pipeline (Ingestion → Storage → Processing → Visualization / Consumption).
  • 2 Clearly distinguish ETL from ELT and know when each pattern is preferred.
  • 3 Compare Data Warehouses, Data Lakes, and Lakehouses and map them to business needs.
  • 4 Explain Batch vs Real-time (streaming) processing with concrete use-cases.
  • 5 Design a simple pipeline for a real scenario (university attendance system).

2. Motivation

Raw data sitting in files, APIs, or operational databases has almost no value until it is moved, cleaned, integrated, and made available for analysis. The system that does this work is called a data pipeline.

A poorly designed pipeline leads to late reports, inconsistent numbers, broken dashboards, and loss of trust. A well-designed pipeline becomes the backbone of every analytics product in the organization.

💡 Key Insight
Analysts who understand pipeline architecture communicate better with data engineers, write more robust queries, and design dashboards that stay reliable as data volume grows.

3. Real-World Story

The Dashboard That Lied for Three Weeks

A retail company launched a new “Daily Sales Health” dashboard. For three weeks the numbers looked healthy. Then finance noticed that regional totals did not match the ERP system.

Root cause: the pipeline that fed the dashboard used an old ETL job that only refreshed product hierarchy once a month. After a major category restructure, many products were mapped to the wrong parent. The dashboard was technically “working” — it was just showing the wrong truth.

The fix required redesigning the pipeline so that reference data (product hierarchy) was treated as a first-class input with its own freshness SLA and validation checks. This lecture teaches you how to think about those design decisions from the start.

4. Problem Statement

The Pipeline Challenge
How do we reliably move data from many sources, transform it into a trustworthy analytical form, store it efficiently, and serve it to analysts and dashboards — while keeping cost, latency, and complexity under control?

5. Theory — End-to-End Pipeline Architecture

A typical analytics pipeline has four major stages:

1. Ingestion

Collect data from operational systems, files, APIs, event streams, and third-party sources. Landing zone is often a raw/bronze layer where data is kept as close to the source as possible.

2. Storage

Persist data in a form that supports both current and future analysis. Choices include data warehouses, data lakes, or modern lakehouses.

3. Processing / Transformation

Clean, validate, join, aggregate, and model the data so that analysts and BI tools can use it safely and efficiently.

4. Consumption

Serve the curated data through SQL endpoints, semantic models, dashboards, notebooks, and APIs.

6. Easy Explanation — Pipeline as a Kitchen

Think of a restaurant kitchen:

  • Ingestion = trucks delivering ingredients (raw data arriving).
  • Storage = pantry and cold room (where ingredients wait).
  • Processing = chefs washing, chopping, cooking (transforming raw into ready-to-serve).
  • Consumption = plates going to tables (dashboards and reports that decision-makers actually use).

If the pantry is disorganized or the chefs use old recipes, the plates will be wrong even if the trucks arrived on time.

7. Deep Explanation — ETL vs ELT

Aspect ETL ELT
Order Extract → Transform → Load Extract → Load → Transform
Where transform happens In a separate ETL engine / staging server Inside the target warehouse / lakehouse
Classic tools Informatica, SSIS, Talend, traditional scripts dbt, Spark, warehouse SQL (BigQuery, Snowflake, Databricks)
Strength Heavy cleansing before data enters the warehouse; good for strict compliance Scalable compute of modern warehouses; raw data retained for re-processing
Typical use Legacy systems, regulated environments, smaller volumes Cloud analytics platforms, large volumes, agile analytics teams
When to prefer which?
  • Choose ETL when you must enforce strict data quality and privacy rules before any data lands in the analytics store.
  • Choose ELT when you want to keep raw history, leverage warehouse compute, and let analysts iterate on transformations quickly (very common today).

8. Data Warehouse vs Data Lake vs Lakehouse

Data Warehouse

Optimized for structured, cleaned, modeled data. Excellent for BI, dashboards, and consistent KPIs. Historically more expensive and less flexible for semi-structured or unstructured data.

Data Lake

Stores raw and processed data in cheap object storage (files). Flexible, but without careful governance it becomes a “data swamp”. Schema is applied when you read the data.

Lakehouse

Modern architecture that brings warehouse reliability (ACID transactions, schema enforcement, time travel) on top of lake storage. Popular platforms: Databricks, Snowflake (with stages), Microsoft Fabric, etc.

9. Batch vs Real-Time Processing

Batch Real-time / Streaming
Latency Minutes to hours (or daily) Seconds to milliseconds
Typical use Daily sales reports, monthly finance close, historical EDA Fraud detection, live inventory, operational dashboards, alerting
Complexity & cost Lower Higher (always-on infrastructure)
Tools (examples) Scheduled SQL, Airflow, dbt, Spark batch Kafka, Flink, Spark Streaming, cloud stream services

Most analytics work still starts with batch. Introduce real-time only when the business genuinely needs low latency and is ready to pay for the operational complexity.

10. Practical — University Attendance Pipeline

Exercise: Design a Pipeline

Scenario: A university wants a dashboard that shows daily attendance by department, course, and student, with the ability to flag students below 75% attendance.

Sketch the pipeline by answering:

  1. What are the source systems? (e.g., biometric devices, LMS, student information system)
  2. Is this primarily batch or real-time? Why?
  3. Would you lean ETL or ELT?
  4. What would you store in a “raw” layer vs a “curated” layer?
  5. Which KPIs would the final consumption layer serve?
Sample Solution Outline +
  1. Sources: Biometric / RFID attendance logs, Student Information System (SIS) for enrollments and demographics, LMS for online session attendance, academic calendar.
  2. Batch is sufficient for most reporting (nightly or hourly). Real-time only if live “who is in class right now” is required.
  3. ELT preferred if using a modern warehouse: land raw logs, then transform with SQL/dbt into attendance facts and dimension tables.
  4. Raw: original device logs and SIS extracts. Curated: fact_attendance, dim_student, dim_course, dim_date, with quality flags.
  5. KPIs: Attendance %, students below threshold, department comparison, trend over weeks, course-level risk list.

11. Industry Examples

  • E-commerce: Clickstream + orders + inventory → near-real-time conversion funnel and stock-out alerts.
  • Banking: Transaction stream → fraud scoring pipeline (real-time) + nightly regulatory aggregates (batch).
  • Healthcare: EHR extracts → nightly clinical quality dashboards; selected vitals streamed for ICU monitoring.
  • Government: Multiple departmental systems → central warehouse for budget vs actual and service-level reporting.

15. Summary & Cheat Sheet

  • A data pipeline moves data from sources to trusted analytical assets.
  • Four stages: Ingestion, Storage, Processing, Consumption.
  • ETL transforms before load; ELT loads first then transforms (modern default).
  • Warehouses excel at structured BI; lakes at flexible storage; lakehouses combine both.
  • Use batch by default; introduce streaming only when latency truly matters.

16. Common Mistakes & Best Practices

Common Mistakes
  • Skipping a raw/landing layer and overwriting source history
  • Treating every pipeline as real-time when batch would suffice
  • No data quality checks between stages
  • Hard-coding business logic in fragile scripts with no version control
Best Practices
  • Keep raw data immutable; build curated layers on top
  • Define freshness and quality SLAs for each critical table
  • Prefer ELT + modular transformations (e.g., dbt-style) when using cloud warehouses
  • Document lineage so every KPI can be traced back to sources
