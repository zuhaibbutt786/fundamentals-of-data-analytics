Lecture 22: Data Modeling

Design analytical models that make measures correct, filters predictable, and reports fast — star schema, facts, dimensions, and relationships.

1. Learning Objectives

  • 1 Distinguish fact tables from dimension tables and give examples of each.
  • 2 Draw a simple star schema and explain why it is preferred for BI.
  • 3 Set relationship cardinality (1:*) and filter direction correctly.
  • 4 Recognize when a snowflake appears and when to flatten.
  • 5 Apply a modeling checklist before writing DAX.

2. Why Modeling Matters

A report is only as trustworthy as the model behind it. Wrong grain, missing keys, or bidirectional filters create totals that look plausible and are wrong. Good models make DAX simpler and performance better.

3. Facts vs Dimensions

Fact tableDimension table
ContainsEvents / transactions / measurementsDescriptive attributes
GrainOne row per event (or defined aggregation)One row per entity (product, customer, date)
KeysForeign keys to dimensions + measuresPrimary key + labels, hierarchies
ExampleSales: date_key, product_key, qty, amountProduct: product_key, name, category

4. Star Schema

One central fact table; dimensions connect only to the fact (not to each other in the pure star). Easy to understand, efficient to query, natural for DAX filter context.

5. Relationships & Cardinality

  • One-to-many (1:*) — dimension (one) → fact (many). Default and preferred.
  • Filter direction — usually single: dimension filters fact.
  • Bidirectional — use sparingly; can create ambiguous paths and wrong totals.
  • Inactive relationships — alternate paths (e.g., order date vs ship date) activated with USERELATIONSHIP in DAX.

6. Snowflake vs Flatten

A snowflake normalizes dimensions (Product → Category → Department). In Power BI, flattening attributes into the dimension table often simplifies filters and improves usability, at the cost of some redundancy.

7. Modeling Checklist

  • ☐ Fact grain is explicit and consistent
  • ☐ Dimension keys unique; fact FKs match
  • ☐ Date table marked and continuous
  • ☐ No many-to-many unless intentionally designed
  • ☐ Hidden technical columns; friendly names
  • ☐ Test: filter a dimension and verify fact totals change correctly

8. Knowledge Check

Q1. Sales amount and quantity belong in:

A. A dimension table only
B. A fact table
C. The report theme
D. A slicer exclusively

9. Summary

  • Star schema: fact in the center, dimensions around it.
  • Correct grain and 1:* relationships make DAX reliable.
  • Model first; measures second.
