Lecture 22: Data Modeling

Design analytical models that make measures correct, filters predictable, and reports fast — fact & dimension tables, star vs snowflake schema, and Power BI relationships.

1. Learning Objectives

  • 1 Distinguish fact tables from dimension tables and give examples of each.
  • 2 Draw a simple star schema and explain why it is preferred for BI.
  • 3 Set relationship cardinality (1:*) and filter direction correctly in Power BI.
  • 4 Recognize when a snowflake appears and when to flatten.
  • 5 Apply a modeling checklist before writing DAX.

2. Motivation — Why Modeling Matters

A report is only as trustworthy as the model behind it. Wrong grain, missing keys, or bidirectional filters create totals that look plausible and are wrong. Good models make DAX simpler and performance better.

💡 Key Insight
Spend time on the model before measures. A clean star schema turns complex DAX into short, readable formulas.

3. Real-World Story

The Double-Counted Revenue

A sales dashboard showed revenue 40% higher than finance. Cause: a many-to-many path between Product and Sales through an intermediate table, plus bidirectional filters. Fixing to a single fact table and one-to-many relationships from dimensions resolved the discrepancy in one day — after weeks of arguing about “which number is right.”

4. Facts vs Dimensions

Fact tableDimension table
ContainsEvents / transactions / measurementsDescriptive attributes
GrainOne row per event (or defined aggregation)One row per entity (product, customer, date)
KeysForeign keys to dimensions + measuresPrimary key + labels, hierarchies
ExampleSales: date_key, product_key, qty, amountProduct: product_key, name, category

Grain is the most important modeling decision: what does one row in the fact table represent? Order line? Daily snapshot? Clarify before building relationships.

5. Star Schema

A central fact table surrounded by dimension tables. Dimensions connect only to the fact (not to each other for filtering the fact). This is the default recommendation for Power BI analytical models.

Figure: Classic star — one fact, multiple dimensions. Filter from dims → fact.

6. Snowflake Schema

Dimensions are normalized into sub-dimensions (e.g., Product → Category → Department). Saves storage in classic warehouses; in Power BI, often better to flatten (denormalize) into fewer wider dimension tables for simpler DAX and filters.

StarSnowflake
StructureFact + denormalized dimsFact + normalized dim hierarchy
DAX complexityLowerHigher (more relationships)
Power BI preferencePreferred for most modelsUse only when necessary

7. Relationships in Power BI

  • Cardinality: usually one-to-many (1:*) from dimension to fact
  • Filter direction: single (dimension filters fact) by default — safest
  • Bidirectional: use rarely; can create ambiguous paths and wrong totals
  • Active vs inactive: multiple paths need USERELATIONSHIP in DAX
Common mistake
Many-to-many relationships without a bridge table or careful measures often double-count. Prefer a proper bridge or a clear grain.

8. Industry Modeling Examples

Retail

Fact: Sales (order line). Dims: Date, Product, Store, Customer, Promotion.

Healthcare

Fact: Encounter or LabResult. Dims: Date, Patient, Provider, Facility, Diagnosis.

Banking

Fact: Transaction. Dims: Date, Account, Customer, Branch, Product type.

Education

Fact: Enrollment or Assessment. Dims: Date, Student, Course, Instructor, Term.

9. Modeling Checklist

  • ☐ Grain of each fact table is written down in one sentence
  • ☐ Every fact has keys to required dimensions
  • ☐ Date table is continuous and marked as date table
  • ☐ Relationships are 1:* from dim → fact; filter direction single unless justified
  • ☐ No ambiguous paths that double-count
  • ☐ Hidden technical columns; friendly names for report fields

13. Flashcards

Fact = events/measures at a grain; Dim = descriptive attributes + key
Star schema?
Central fact + surrounding dimensions; preferred for BI
Default cardinality?
1:* from dimension to fact; single filter direction
Snowflake tip in Power BI?

14. Cheat Sheet

  • Fact: events at clear grain + FKs + measures
  • Dim: one row per entity + PK + attributes/hierarchies
  • Star: fact in center; dims around; filters dim → fact
  • Relationships: 1:* · single direction · avoid accidental many-to-many
  • Before DAX: fix grain, keys, date table, filter paths

15. Summary

  • Separate facts (events/measures) from dimensions (descriptors).
  • Prefer star schema for Power BI analytics.
  • Set 1:* relationships with single filter direction unless you have a clear reason.
  • Document grain; validate keys before writing complex DAX.
