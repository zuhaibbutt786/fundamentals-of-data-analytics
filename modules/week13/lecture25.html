Lecture 25: Performance Optimization

Avoid circular dependencies, optimize the model, remove redundant columns, and write DAX that stays fast as data grows — syllabus focus for production-ready models.

1. Learning Objectives

  • 1 Recognize and resolve circular dependency errors in calculated columns/measures.
  • 2 Reduce model size by removing unused and high-cardinality columns.
  • 3 Prefer measures over calculated columns when appropriate for memory.
  • 4 Apply a practical optimization checklist before publishing a dashboard.
  • 5 Explain why star schema and single-direction filters help performance.

2. Motivation

A model that works on 10,000 rows can freeze on 10 million if it is full of redundant columns, bidirectional filters, and heavy calculated columns. Optimization is not optional for real deployments — it is part of professional modeling.

3. Avoiding Circular Dependency

A circular dependency occurs when calculation A depends on B and B depends on A (directly or through a chain). Power BI cannot determine an evaluation order.

Typical causes
  • Calculated column A references column B, and B references A
  • Measures and columns intertwined through tables incorrectly
  • Relationships plus calculated columns creating evaluation loops

Fix: break the cycle — compute base columns first, or move logic into measures that do not write back into the same dependency chain.

4. Optimizing the Model

  • Remove unused tables and columns — less memory, faster refresh
  • Reduce cardinality — avoid unique text IDs in fact tables when a surrogate key exists
  • Prefer integers for keys — smaller and faster than long strings
  • Star schema + single filter direction — simpler query plans
  • Disable Auto Date/Time if you already have a proper DimDate
  • Aggregate facts when the report never needs transaction grain

5. Removing Redundant Columns

Columns that are never used in visuals, filters, or relationships still consume memory (especially high-cardinality text). After building the report, audit fields and drop what is unused — or hide technical keys that users should not see.

Practical tip
Start with a simple “used in report?” checklist. On larger models, tools such as VertiPaq Analyzer help find the heaviest columns.

6. DAX Efficiency Habits

  • Prefer measures over calculated columns for aggregations
  • Use VAR to avoid recomputing the same expression
  • Avoid iterators over huge tables when a simple aggregation works
  • Filter early; do not scan the entire fact when a dimension filter would do
  • Test measures with Performance Analyzer on slow visuals

7. Hands-on Lab

  1. List every column in your practice model; mark used vs unused.
  2. Remove or hide at least three unused columns; note any refresh change.
  3. Confirm no bidirectional filters remain without justification.
  4. Rewrite one calculated column as a measure if it was only used for aggregation.
  5. Document one circular dependency scenario and how you would break it.

8. Interview & Viva Questions

  • What causes a circular dependency in Power BI?
  • How do you reduce model memory size?
  • Why can calculated columns be more expensive than measures?
  • What is the benefit of a star schema for performance?

9. Knowledge Check

D. CSV import failed

B. Remove unused / high-cardinality columns

D. Duplicate fact tables

Q3. For aggregations, prefer:

A. Many calculated columns only
B. No measures ever

10. Flashcards

Circular dependency?
A depends on B and B on A — break the cycle
Model slim-down?
Drop unused columns · lower cardinality · integer keys
Measures vs columns (perf)?
Measures usually cheaper for aggregations; columns stored
Schema for speed?
Star + single-direction filters + clean relationships

11. Cheat Sheet

  • Break circular deps; do not force mutual calculated columns
  • Remove unused columns; hide technical keys
  • Prefer measures; use VAR; avoid needless iterators
  • Star schema · 1:* · single filter direction
  • Disable Auto Date/Time if DimDate exists

12. Summary

  • Circular dependencies must be broken, not ignored.
  • Model size is dominated by columns you keep — audit and remove.
  • Good schema and measure design are performance features.
